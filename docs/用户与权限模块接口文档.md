# 用户与权限模块接口文档（含业务逻辑）

## 1. 通用约定
- 基础地址：`http://localhost:8081`
- 统一返回：`Result<T>`，`code=1` 成功，`code=0` 失败。
- 除登录/注册接口外，其余接口需要在请求头携带用户或管理员 token。
- 关键状态定义：
  - 用户角色：`1=普通用户`，`2=卖家`
  - 用户状态：`1=正常`，`2=禁用`
  - 卖家认证状态：`0=待审核`，`1=已通过`，`2=已驳回`，`3=已撤回`

## 2. 用户端接口

### 2.1 `POST /user/register`
- 作用：注册普通用户账号。
- 参数校验：
  - `studentNo` 必填，6-20 位字母或数字。
  - `password` 必填，6-20 位且不能包含空格。
  - `name` 选填，长度与字符格式受限。
  - `phone` 选填，必须是合法手机号。
- 业务规则：
  - 学号必须唯一。
  - 手机号（如果填写）必须唯一。
  - 默认注册为普通用户角色、正常状态。

### 2.2 `POST /user/login`
- 作用：用户统一登录（普通用户和卖家共用）。
- 参数校验：
  - `account`、`password` 必填。
  - `account` 必须是合法学号或手机号。
- 业务规则：
  - 按学号或手机号查询用户。
  - 校验密码（MD5）正确。
  - 仅状态为正常的用户可登录。
  - 登录成功后签发用户 JWT，返回 `role` 给前端决定功能展示。

### 2.3 `POST /user/login/buyer`（兼容旧地址）
- 作用：兼容旧前端地址。
- 业务规则：内部复用 `POST /user/login` 统一逻辑，不再区分买家/卖家登录口。

### 2.4 `POST /user/login/seller`（兼容旧地址）
- 作用：兼容旧前端地址。
- 业务规则：内部复用 `POST /user/login` 统一逻辑，不再区分买家/卖家登录口。

### 2.5 `GET /user/profile`
- 作用：查询当前登录用户资料。
- 业务规则：
  - 必须已登录（从 JWT 解析 userId）。
  - 当前用户必须存在。

### 2.6 `PUT /user/profile`
- 作用：修改当前用户资料。
- 参数校验：
  - 至少传一个可更新字段。
  - `name` 格式合法。
  - `phone` 格式合法且不能与其他账号重复。
  - `avatar` 必须是 `http/https` URL。
  - `campus` 长度不超过 50。
  - `intro` 长度不超过 255。
- 业务规则：
  - 只能修改当前登录用户。

### 2.7 `DELETE /user/profile`
- 作用：注销当前账号。
- 业务规则：
  - 卖家账号不允许自助注销。
  - 若存在待审核卖家认证申请，不允许注销。
  - 仅满足条件时执行删除。

### 2.8 `POST /user/upload`
- 作用：上传用户相关文件到 OSS。
- 参数校验：
  - `file` 必传，且非空。
  - 文件大小 ≤ 5MB。
  - 文件后缀仅允许：`jpg/jpeg/png/webp/gif/pdf`。
  - `category` 仅允许：`common/avatar/goods/seller-auth`（默认 `common`）。
- 业务规则：
  - 上传失败返回统一错误信息，不透出底层异常细节。

### 2.9 `POST /user/seller-auth/apply`
- 作用：提交卖家认证申请。
- 参数校验：
  - `realName` 必填且格式合法。
  - `phone` 必填且格式合法。
  - `material` 必填且必须是 URL。
  - `studentNo` 若传入，必须与当前登录用户学号一致。
- 业务规则：
  - 仅普通用户可申请；卖家或其他角色不可申请。
  - 用户状态必须为正常。
  - 存在待审核申请时不能重复提交。
  - 已通过认证的用户不能重复提交。
  - 新申请写入状态为待审核。

### 2.10 `GET /user/seller-auth/result`
- 作用：查询当前用户最近一次卖家认证结果。
- 业务规则：
  - 仅登录用户可查询。
  - 无历史申请记录时返回业务错误。

### 2.11 `GET /user/seller-auth/portal`
- 作用：卖家权限校验示例接口。
- 业务规则：
  - 仅卖家角色可访问。

## 3. 管理端接口

### 3.1 `POST /admin/login`
- 作用：管理员登录。
- 参数校验：
  - `username`、`password` 必填。
  - `username` 需符合管理员账号格式。
- 业务规则：
  - 管理员账号必须存在。
  - 密码校验通过。
  - 账号状态必须为正常。
  - 登录成功签发管理员 JWT。

### 3.2 `POST /admin/admin`
- 作用：新增管理员。
- 参数校验：
  - `username` 必填且格式合法。
  - `name` 必填且格式合法。
  - `phone` 选填，若传需合法。
  - `status` 仅允许正常/禁用。
  - `password` 为空时使用默认密码，且仍校验密码规则。
- 业务规则：
  - `username` 必须唯一。

### 3.3 `PUT /admin/admin`
- 作用：修改管理员信息。
- 参数校验：
  - `id` 必填。
  - 传入字段按规则校验（账号/密码/名称/手机号/状态）。
  - 更新账号时检查唯一性（排除当前 id）。
- 业务规则：
  - 目标管理员必须存在。
  - 不允许禁用当前登录管理员。
  - 系统必须至少保留一个正常状态管理员。

### 3.4 `DELETE /admin/admin/{id}`
- 作用：删除管理员。
- 业务规则：
  - 目标管理员必须存在。
  - 不允许删除当前登录管理员。
  - 若目标为最后一个正常管理员，不允许删除。

### 3.5 `GET /admin/admin/{id}`
- 作用：按 id 查询管理员。
- 业务规则：
  - `id` 必填，且必须存在。

### 3.6 `GET /admin/admin/page`
- 作用：分页查询管理员。
- 参数校验：
  - 页码/页大小自动兜底为正数默认值。
  - `status` 若传入必须合法。

### 3.7 `GET /admin/seller-auth/page`
- 作用：分页查询卖家认证申请。
- 参数校验：
  - 页码/页大小自动兜底。
  - `status` 为空时默认查待审核；不为空时必须合法。
- 业务规则：
  - 支持按姓名、手机号、学号筛选。

### 3.8 `PUT /admin/seller-auth/audit`
- 作用：审核卖家认证（通过/驳回）。
- 参数校验：
  - `authId`、`status` 必填。
  - `status` 仅允许 `1(通过)` 或 `2(驳回)`。
  - 驳回时 `reason` 必填，且长度 ≤ 255。
- 业务规则：
  - 认证申请必须存在且当前状态必须为待审核。
  - 审核通过前会校验申请用户存在且处于正常状态。
  - 审核通过后将用户角色升级为卖家。
  - 审核与角色升级在同一事务中完成，任一步失败整体回滚。

## 4. 异常处理与安全
- 统一拦截 `BaseException` 返回业务错误信息。
- 统一拦截数据库唯一键冲突。
- 增加未知异常兜底处理，避免异常泄漏。
- JWT 拦截器在请求前后都会清理 `BaseContext`，防止线程复用导致用户串号。
