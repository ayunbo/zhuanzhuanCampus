# 聊天与通知模块统一说明 + 接口规范（兼容现有项目风格最终版）

## 1. 文档用途
本文档用于统一 **聊天模块** 和 **通知模块** 的业务理解、前后端接口风格、命名规范、返回格式、WebSocket 消息格式。  
目标是让不同 AI、不同前后端代码都按同一套规则生成，避免风格混乱、字段不一致、接口命名冲突。

本文档必须 **兼容当前项目已有风格**：

- 已有用户端路径风格：`/user/...`
- 已有管理端路径风格：`/admin/...`
- 统一返回：`Result<T>`，`code=1` 成功，`code=0` 失败
- 登录后依赖 JWT，从 `BaseContext` 中获取当前用户 id
- 除登录/注册等公开接口外，其余接口默认都需要 token

## 2. 项目背景
本项目是一个 **校园二手商品交易系统**，整体为前后端分离单体架构：

- 后端：SpringBoot + Spring + MyBatis
- 认证：JWT
- 数据库：MySQL
- 缓存：Redis

- 实时通信：WebSocket

我只负责两个模块，而且 **前后端都由我开发**：

1. 聊天模块
2. 通知模块

## 4. 业务统一理解

## 4.1 聊天模块的本质
聊天不是普通社交私聊，而是 **围绕商品交易场景的沟通能力**。

### 会话唯一规则
一个聊天会话由以下三项唯一确定：

- `goodsId`
- `buyerId`
- `sellerId`

即：

- 同一个商品
- 同一个买家
- 同一个卖家

只应存在一个会话。

### 重要补充：同一用户既可以是卖家，也可以是买家
一个用户在系统全局中，可能既卖东西，也买别人的东西。  
因此：

- 不要根据用户表全局 `role` 去决定某个聊天会话里的身份
- 必须根据当前 `chatsession` 里的 `sellerId`、`buyerId` 来判断当前用户在该会话中的身份

规则如下：

- 如果 `currentUserId == session.sellerId`，则当前用户在该会话中是卖家
- 如果 `currentUserId == session.buyerId`，则当前用户在该会话中是买家
- 否则无权访问该会话

也就是说：

- 用户 A 在会话 1 中可以是卖家
- 用户 A 在会话 2 中也可以是买家

这不冲突。

### 聊天不是按订单唯一
聊天会话按 `商品 + 买家 + 卖家` 唯一，**不是按订单唯一**。

---

## 4.2 通知模块的本质
通知模块本质上是一套 **统一的站内通知能力**。

以下业务虽然来源不同，但实现上都属于同一套通知系统：

- 卖家认证审核结果
- 商品审核结果
- 订单状态变化
- 举报处理结果
- 其他系统通知

它们的共同点：

1. 某个业务事件发生
2. 生成通知记录
3. 写入 `notice` 表
4. 在通知列表中展示
5. 支持已读/未读
6. 在线用户可走 WebSocket 推送

所以：

- 它们是 **不同来源的通知**
- 不是 **四套独立的通知系统**

### 重要补充：通知的后端语义与前端呈现可以分离
本项目中，**通知仍然是通知**，后端语义不改，仍然按通知模块设计：

- 通知记录继续写入 `notice` 表
- 通知查询、未读统计、已读操作接口继续使用 `/user/notice/...`
- 通知不要求写入 `chatmessage`
- 通知不要求创建真实的 `chatsession`

但在前端表现层，允许把通知统一渲染成一个 **“系统通知 / 系统消息”会话窗口**：

- 前端可以把通知列表伪装成聊天气泡样式
- 每条 `notice` 记录都可以渲染成一条系统消息气泡
- 这是前端 UI 策略，不代表通知模块在后端被改造成聊天模块

换句话说：

- 后端仍然维护“通知”
- 前端可以把它展示成“系统会话”

---

## 4.3 前端统一消息入口
为了提升消息中心的一致性，前端允许将“用户聊天”和“系统通知”统一收口到同一个消息入口中。

具体约定如下：

- 普通用户聊天会话，数据来源仍然是 `chatsession + chatmessage`
- 系统通知会话，是前端虚拟出来的一个特殊会话，数据来源是 `notice`
- 该系统通知会话可以固定出现在会话列表中，与普通聊天会话并列展示
- 系统通知会话的最后一条内容，可由最新一条 `notice.title / notice.content` 推导
- 系统通知会话的未读数，可直接使用通知未读总数

这意味着前端可以做成下面这种体验：

- 左侧是统一的会话列表
- 其中既有用户之间的真实聊天会话
- 也有一个“系统通知”会话
- 点进“系统通知”后，右侧按聊天气泡样式展示通知流

这个“系统通知会话”只是前端视图模型，不是数据库里的真实聊天会话。

## 5. 数据库相关表

## 5.1 核心表

### `chatmessage`
字段重点：

- `id`
- `session_id`
- `sender_id`
- `receiver_id`
- `type`：1文本 2图片 3系统
- `content`
- `read_status`
- `read_time`
- `create_time`

用途：

- 保存每条聊天消息
- 查询历史消息
- 已读/未读维护

### `chatsession`
字段重点：

- `id`
- `goods_id`
- `seller_id`
- `buyer_id`
- `goods_title`
- `goods_cover`
- `last_msg`
- `last_time`
- `seller_unread`
- `buyer_unread`

关键约束：

- 唯一索引：`goods_id + seller_id + buyer_id`

用途：

- 保存会话基本信息
- 保存最后一条消息摘要
- 保存会话级未读数

### `notice`
字段重点：

- `id`
- `user_id`
- `type`：1订单 2审核 3举报 4系统
- `title`
- `content`
- `biz_type`：1商品 2订单 3卖家认证 4聊天 5举报
- `biz_id`
- `read_status`
- `read_time`
- `create_time`

用途：

- 保存所有站内通知
- 支持列表、未读统计、已读状态
- 作为前端“系统通知会话”的数据源

## 6. 默认实现口径

## 6.1 聊天模块默认口径
### 一期范围
- 默认先只做 **文本消息**
- 虽然数据库预留了图片消息类型，但当前一期不做图片聊天

### 会话规则
- 前端进入聊天页时，根据 `goodsId + buyerId + sellerId` 获取会话
- 如果会话不存在，则创建
- 如果会话已存在，则直接返回已有会话

### 消息发送规则
发送消息后，后端需要：

1. 插入 `chatmessage`
2. 更新 `chatsession.last_msg`
3. 更新 `chatsession.last_time`
4. 给对方未读数 +1

未读数规则：

- 如果发送者是 `buyerId`，则 `seller_unread + 1`
- 如果发送者是 `sellerId`，则 `buyer_unread + 1`

### 已读规则
用户进入会话并查看消息后：

1. 将“发给当前用户且未读”的消息批量改为已读
2. 更新 `chatmessage.read_status = 1`
3. 更新 `read_time`
4. 清空当前用户在该会话中的未读数：
   - 当前用户是买家：`buyer_unread = 0`
   - 当前用户是卖家：`seller_unread = 0`

### 会话列表规则
会话列表查询条件为：

- `seller_id = currentUserId`
- 或 `buyer_id = currentUserId`

每条会话需要返回：

- 当前用户在该会话中的身份 `myRole`
- 对方用户信息
- 商品信息
- 最后一条消息摘要
- 最后消息时间
- 当前用户未读数

---

## 6.2 通知模块默认口径
### 当前只做
- 站内通知
- WebSocket 在线推送

### 当前不做
- 邮件通知
- 短信通知
- 微信通知

### 通知统一处理逻辑
所有通知统一走一套逻辑：

1. 某业务事件触发
2. 调用通知服务
3. 生成通知记录
4. 写入 `notice`
5. 用户在线则 WebSocket 推送
6. 用户查看后改为已读

### 前端呈现策略
通知模块在前端允许采用“系统聊天窗口”的方式展示，但后端职责保持不变：

- 后端仍然提供 `/user/notice/...` 接口
- 前端允许把通知列表渲染成一个“系统通知”会话页面
- 每条通知渲染成一条系统气泡消息
- 前端不需要要求后端把通知改存到 `chatmessage`
- 前端不需要要求后端为通知额外创建真实 `chatsession`

因此，通知详情的默认查看方式可以不是传统“通知详情页”，而是：

- 在消息中心进入“系统通知”会话
- 通过消息流方式查看历史通知
- 必要时再根据 `bizType + bizId` 跳到具体业务详情页

### 在线提醒策略
在线提醒允许统一使用“顶部胶囊弹窗”这一套交互外观。

适用来源：

- 用户聊天新消息
- 系统通知推送

交互约定：

- 新消息到达时，可在页面顶部从上向下弹出胶囊提醒
- 点击聊天提醒，跳转到聊天页并选中对应聊天会话
- 点击系统通知提醒，跳转到聊天页并选中“系统通知”会话
- 如果通知本身绑定了业务对象，前端也可以在进入系统通知会话后，再引导用户查看对应业务详情

这里的“顶部胶囊弹窗”属于前端统一消息体验，不要求后端改变通知模型或聊天模型

## 7. 兼容现有项目的接口风格总原则

## 7.1 路径前缀
为了兼容现有项目，不再使用 `/api/chat/...` 这种新前缀，统一改为：

### 用户端
- `/user/chat/...`
- `/user/notice/...`

即使前端把通知渲染进聊天页，通知相关接口也仍然保持：

- 查询通知：`/user/notice/...`
- 通知已读：`/user/notice/...`
- 通知未读统计：`/user/notice/...`

不要因为前端做成“系统会话”，就把通知接口改挂到 `/user/chat/...` 下面。

### 管理端
当前聊天和通知模块一期默认只做用户端，不单独开放管理员聊天/通知接口。  
如果后续需要管理端接口，再使用：

- `/admin/chat/...`
- `/admin/notice/...`

---

## 7.2 HTTP 方法规范
统一规则：

- `GET`：查询
- `POST`：新增 / 创建 / 发送 / 批量业务动作
- `PUT`：完整修改
- `PATCH`：状态修改
- `DELETE`：删除

结合现有项目风格，允许保留少量动作型路径，如：

- `/user/notice/read-all`
- `/user/chat/session/read`

但整体仍尽量保持资源式设计。

---

## 7.3 JSON 字段规范
所有前后端 JSON 字段统一使用 **camelCase**，例如：

- `sessionId`
- `goodsId`
- `buyerId`
- `sellerId`
- `lastMsg`
- `createTime`

数据库字段可使用下划线，接口 JSON 一律驼峰。

---
