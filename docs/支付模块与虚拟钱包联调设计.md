# 支付模块与虚拟钱包联调设计

## 简化目标

- 保留现有 `mock` 模拟支付
- 新增一个轻量版“虚拟钱包支付”
- 虚拟钱包是外部独立 App
- 钱包用户和校园平台 `user` 不是同一个体系
- 只支持两种资金来源：
  - 钱包余额
  - 银行卡余额
- 用户输入支付密码后完成支付
- 如果余额不足，则支付失败

## 简化后的数据表

- `wallet_account`
  - 外部钱包 App 自己的账户
  - 存 `balance`
  - 存 `pay_password`
  - 不关联平台 `user.id`

- `wallet_bank_card`
  - 钱包绑定银行卡
  - 每张卡也有独立 `balance`

## 支付流程

### 1. 模拟支付

- 继续走你当前已有流程
- 不改

### 2. 虚拟钱包支付

用户在支付页选择：

- `钱包余额`
- `银行卡`

然后输入支付密码。

服务端判断：

- 如果支付渠道是 `钱包余额`
  - 判断 `wallet_account.balance >= 订单金额`
  - 足够则扣减余额并支付成功
  - 不足则支付失败

- 如果支付渠道是 `银行卡`
  - 判断 `wallet_bank_card.balance >= 订单金额`
  - 足够则扣减银行卡余额并支付成功
  - 不足则支付失败

密码错误也直接支付失败。

## 账户关系说明

- 平台用户：你当前系统里的 `user`
- 钱包用户：虚拟钱包 App 里的 `wallet_account`
- 两者不做绑定
- 平台只关心：
  - 哪笔 `order` 发起了支付
  - 哪个钱包账户完成了支付
  - 最终是否支付成功

这意味着：

- 同一个钱包账户可以为多个平台用户的订单支付
- 一个钱包 App 可以有多个钱包用户切换登录
- 平台无需知道钱包账户是否属于当前下单用户

## 为什么可以不改表结构

- 现有 `pay` 仍然是主支付单
- 现有 `pay_record` 仍然是平台支付记录
- 新增的 `wallet_*` 表只负责钱包页面展示和扣款来源
- 这样订单模块和原支付模块都不用推翻

## 这版先不做

- 冻结金额
- 退款
- 提现
- 复杂签名
- 多阶段回调
